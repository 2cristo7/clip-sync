# ClipSync Security Model — Phase 4

This document describes how the macOS server in `mac/ClipSync` defends the
clipboard sync transport. The model is intentionally tuned for a LAN-only
two-device link (laptop ↔ phone) and trades CA-issued PKI for a TOFU
(trust-on-first-use) bond established during pairing.

## Threat model recap

- **Attacker on the LAN** can sniff frames, run a rogue HTTP server on the
  same port, and attempt to inject clipboards.
- **Attacker on a different LAN** (e.g. coffee-shop guest network) cannot
  reach `0.0.0.0:7010` and is out of scope.
- **Compromised paired device** can read the user's clipboard for the
  duration of the pairing — there is no defence against that beyond
  revoking the device.

## Trust establishment (TOFU over pairing)

1. On first launch, the Mac generates and persists in Keychain
   (service `com.clipsync.tls-identity`):
   - An EC P-256 private key (PEM-encoded SEC1).
   - A self-signed X.509 certificate (DER-encoded). SAN entries cover
     `localhost`, `<hostname>.local` and the host's primary IPv4
     address. Validity: 5 years.
2. The certificate's **SubjectPublicKeyInfo SHA-256**, base64url-encoded
   without padding, is the **stable fingerprint** (`fp`) advertised in
   the Bonjour TXT record (`_clipsync._tcp`).
3. When the user starts pairing, the Mac shows a 6-digit code. The
   client (e.g. the Pixel app) connects to the Mac, performs a TLS
   handshake, **records the SPKI fingerprint**, calls
   `GET /pair?code=<digits>` over HTTPS to obtain a Bearer token, and
   pins the recorded fingerprint forever.
4. From that point on, any TLS handshake whose SPKI does not match the
   pinned `fp` is rejected by the client (cert pinning), defeating LAN
   MITM.

## Authentication and integrity

- **`/health`** and **`/pair?code=…`** are reachable without auth.
  `/pair` is rate-limited by the single-use code semantics in
  `PairingManager`.
- **`/inject`** requires `Authorization: Bearer <token>` AND
  `X-ClipSync-Signature: t=<unix_ts>, v1=<hex>` where
  `v1 = HMAC-SHA256(pairing-secret, "<ts>.<body>")`. Timestamps must be
  within ±60 s of server time (replay window). Bad bearer ⇒ 401. Bad
  HMAC ⇒ 401.
- **`/ws`** WebSocket upgrade requires
  `Authorization: Bearer <token>`. The upgrade handshake itself is
  rejected (`dontUpgrade`) when the bearer is missing or invalid.

The Bearer token is generated by `PairingManager.consume(...)` (32
random bytes, base64) and immediately registered in `TokenStore`.
`TokenStore` only ever persists the SHA-256 hex digest of each token —
the plaintext only travels once over TLS at issuance and lives in the
client's secure storage from then on.

## Rotation and revocation

- **Pairing-secret rotation.** The pairing secret in
  `com.clipsync.pairing-secret` underlies HMAC validation. Deleting the
  Keychain item causes the next launch to mint a fresh secret, which
  immediately invalidates every previously-issued HMAC signature
  (signed payloads stop verifying), and therefore every Bearer token in
  `TokenStore` becomes useless because clients cannot send valid
  `/inject` payloads anymore. Operators rotate the secret to perform a
  global revocation.
- **TLS-identity rotation.** Deleting the `tls-cert-der` and
  `tls-key-pem` Keychain entries forces a new self-signed cert on the
  next launch, which changes the SPKI fingerprint. Already-paired
  clients must re-pair because their pinned fingerprint no longer
  matches.
- **Per-device revocation.** `TokenStore.revoke(id:)` removes a single
  device's token. Subsequent `/inject` and `/ws` requests from that
  device receive 401. The intended UI surface is a future menu-bar
  entry: `Clients → <device label> → Revoke`. The data model is in
  place (`TokenStore.list()` returns all records sorted by
  `createdAt`); the menu wiring is left to a follow-up phase.

## Threats not covered

- **Server-side clipboard exfiltration** by a malicious paired device
  is by-design out of scope: pairing means trusting the device.
- **Attacks on Keychain** (e.g. an attacker with the Mac's login
  password) can read both the pairing secret and the TLS private key.
  The data-at-rest threat model is delegated to macOS Keychain ACLs.
- **Compromise of CryptoKit / NIOSSL** is out of scope.
